Research code that survives review: tests as the contract

Industry code that is wrong gets a bug report; research code that is wrong gets published. Your analysis script runs once, by you, and its output becomes a claim with your name on it - which is why "it ran without errors" was never the bar. This session sets the real bar (the one JOSS reviewers, artifact evaluators and the NeurIPS checklist actually apply), then shows the one workflow that makes AI-assisted coding safe for science: you write the test that encodes the truth, the model writes the code, and the test - not your optimism - decides.

Part 1 · the bar

Why research code is different, and what reviewers now check 7 min live

Research code has a brutal property: it typically runs once, on one dataset, operated by its author - and its correctness IS the result. There is no user base to find the off-by-one for you. The venues have noticed, and the expectations are no longer informal.

LiveThe four bars, in the venues' own terms5 min▶
  • JOSS (Journal of Open Source Software) requires an objective way to verify that the software works: its review criteria rate an automated test suite plus continuous integration as "Good", documented manual steps as merely OK, and no verification procedure as not acceptable. A reviewer literally cannot pass your submission without it.
  • ACM artifact badging stamps papers with badges: Artifacts Available (archived and findable), Artifacts Evaluated - Functional (they run and do what is documented), and Results Reproduced (an independent party regenerated your numbers). The badge names are the reproducibility ladder in miniature.
  • The NeurIPS paper checklist asks authors point blank about random seeds, error bars, and whether the paper provides the information needed to reproduce the main results. Answering "no" in public is its own deterrent.
  • Journal data and code availability policies - PLOS is a clear example - require statements about where data and code live. The direction of travel across publishers is one way: toward more required sharing, not less. Verify the current version of your target journal's policy before you submit.
Self-studyThe once-run trap, spelled out3 min read▶

Industrial code fails loudly and repeatedly in front of thousands of users, so bugs surface. Research code fails once, quietly, in front of the one person with the strongest incentive to believe the output. Three consequences worth internalising:

  • Your most dangerous bug produces a plausible number. A sign flip, a dropped group in a merge, a filter applied twice - each yields output that looks like a result and reads like a finding.
  • Review will not catch it. Manuscript reviewers see your prose and figures, not your join logic. The venue mechanisms in the figure above exist precisely because prose review cannot see code.
  • You are the QA department. Which is not a burden so much as a role clarification - and the whole point of Part 2 is that the role is cheap to perform if you encode what you know into tests.
Part 2 · the workflow

AI-assisted coding with tests as the contract 8 min live

There is now peer-reviewed guidance for exactly this: "Twelve quick tips for AI-assisted coding in science" (PLOS Computational Biology, 2026). Its spine matches this session's: prepare the problem before prompting, manage what context the model sees, test and validate everything, and accept that you become the reader and reviewer of code you did not type - while keeping full responsibility for it. The workflow below is that guidance made mechanical.

LiveWhat a known-answer test looks like for analysis code4 min▶

Not abstract software engineering - a tiny dataset where you can compute the truth by hand:

  • For a cleaning function: six rows you wrote yourself, two with the known defect (a duplicate ID, an impossible date). Assert the function returns exactly four rows and exactly the right four.
  • For a statistical step: a toy input whose correct output you computed by hand or with a trusted reference implementation. Assert equality to sensible precision.
  • For a whole pipeline: a miniature input fixture and one number the full run must produce from it. This is the test that catches the refactor that "worked" but reordered a filter.

The pattern generalises: every test is a small place where the truth is known independently of the code. That independence is what lets it judge AI output - the model never saw the answer key.

Self-studyThe twelve-tips spine, mapped to your week3 min read▶
  • Prepare the problem. Decompose before prompting: one function, one contract, one test. Models are dramatically better at well-scoped tasks, and so is your review of them.
  • Manage context. Give the model your data's actual shape - column names, dtypes, a few example rows (never sensitive data; b1's rule 3 still applies). Most "AI wrote wrong code" stories are "AI guessed the schema" stories.
  • Test and validate. The loop above. Run the suite every time the model touches anything - a passing suite is the only sentence in the conversation you can trust unconditionally.
  • You are the reader-reviewer. Read every line you keep. Accepting code you do not understand into an analysis whose correctness is the result is not delegation; per the PLOS guidance, the responsibility never moved.
Part 3 · the audit

Code vs methods: the discrepancy no tool closes 5 min live

Tests check the code against your intent. One gap remains: the code against your PAPER. What your methods section says you did and what your script actually does can drift apart - a threshold changed in week eight, an exclusion added during revision - and that gap is now formally studied.

LiveThe evidence, and the ritual it dictates4 min▶

SciCoQA (ACL 2026) catalogued 635 real discrepancies between published papers and their released code, then asked the best available LLMs to find them: they caught only 46.7%. So the honest division of labour writes itself - AI can assist the audit, flagging candidate mismatches faster than you would, but more than half the real discrepancies get past it. The human read is not a formality; it is the majority of the detection power.

The audit ritual, before every submission:

  • One pass reading the methods section with the code open. Every number in the prose - thresholds, exclusions, model settings - gets pointed at the line that implements it. No line, no sentence.
  • One known-answer reproduction. Fresh environment, one command, and check that a headline number matches the manuscript. Demo 2 builds exactly this.
  • One seed-change robustness check. Change the seed, rerun. Your point estimates should wobble within reason and your conclusions should not move. A conclusion that dies with the seed was never a conclusion.
Real world

The drift is rarely dishonest - that is what makes it common. The methods section was written in month three; the exclusion rule changed in month seven during revision; nobody reread the prose against the diff. The 635 catalogued cases are largely this: honest drift, published. The ritual costs an afternoon; the correction notice costs more.

Self-studyWhat this audit is, and what it is not2 min read▶
  • It is narrower than a code review. You are not judging style or architecture; you are checking that prose and implementation tell the same story. That narrowness is why it fits in an afternoon.
  • It is not the claim-vs-source audit. Checking whether your citations support the sentences attached to them is a different ritual, owned by the AI + Research course (learn-ai-research-with-phoebe). This session's audit stays inside your own repository.
  • It is not the statistics check either. Whether the analysis you correctly implemented was the right analysis - forking paths, multiple comparisons, AI-assisted analysis pitfalls - is b7, next session. Correct code running the wrong analysis passes every test on this page.
Demo 1 of 2

One function, one test, one arbitrated refactor ★ 12 min · everyone builds

Bring one real function from your actual analysis pipeline - a cleaner, a scorer, a transform. Not a toy: the point is to leave with YOUR code safer than it was at minute zero.

Pick the function whose failure would most embarrass you in print. That instinct is a good test-priority ranking, and it is free.

Build the known answer: construct a tiny input (5-10 rows is plenty) where you can state the correct output by hand. Include one edge case you know is nasty - the missing value, the duplicate, the boundary date.

Write the pytest: test_yourfunction_known_answer asserting the exact expected output. Run it against the current implementation. If it fails NOW, congratulations - the session already paid for itself; fix that first.

Ask AI to refactor the function - clearer, faster, vectorised, whatever you actually want. Paste the function and the test; ask for an implementation that passes the test.

Run the suite on the draft. Pass: read every line, then keep it. Fail: send the failure output back and iterate. Notice what you are NOT doing - eyeballing two versions and deciding which "looks right". The test arbitrates; you review.

★ Try it now - the refactor request with the contract attached

Here is a function from my analysis pipeline and the pytest that defines its required behaviour: [paste both]. Refactor the function for clarity and speed. Hard constraints: the test must still pass unchanged, the function signature stays the same, and behaviour on edge cases in the test is non-negotiable. If any part of the required behaviour seems wrong or ambiguous to you, say so explicitly instead of silently changing it.

The version that inherits every mistake

"Rewrite my analysis script to be cleaner" - no test, no contract, whole script at once. Whatever comes back will look better and might be wrong in ways nothing will ever check. You just swapped code you understood for code you have not read, in the one codebase where correctness is the result.

Demo 2 of 2

The mini repro package ★ 10 min · everyone builds

The smallest package that lets someone else reproduce one number from your current project. This is the seed of the ACM Functional badge, the NeurIPS reproduction answer and the JOSS verification story, built in ten minutes.

Pin the environment: export your dependencies with versions (a requirements.txt or environment file). "pandas" is a hope; "pandas==2.2.1" is an environment.

Pin the randomness: one seed, set in one visible place at the top of the pipeline, never scattered through the code.

Write the README run command: install line, run line, and the sentence "this should print [your number]". One command, one expected output - that sentence is the reproducibility claim in miniature.

Reproduce it yourself, hostile-witness style: fresh terminal, fresh environment, follow only the README. Every stumble you hit is a stumble your reviewer hits - fix the README, not the reviewer.

Best version: hand it to a colleague and trade - you run theirs, they run yours. Ten minutes each, and both projects now have independently reproduced numbers. That is Results Reproduced culture at lab scale.

CI, the five-minute version Continuous integration just means your tests run automatically on every push - GitHub Actions does this with one small config file, and AI assistants write that file well (it is boilerplate, their home turf - and the tests judging the result are already yours). For a JOSS submission this is the difference between "OK" and "Good" on the verification criterion. Verify the current version of the criteria on the JOSS review page when you submit.
Homework

Try it yourself - this week ◐ 40-50 min total

  • Extend Demo 1: known-answer tests for the two next-scariest functions in your pipeline. Three tested functions is a test suite; a test suite is a JOSS answer.
  • Run the code-vs-methods pass on your current draft: every number in the methods prose pointed at the line that implements it. Log every mismatch you find - that log is your revision to-do list.
  • Run the seed-change robustness check on your headline result and write one sentence about what moved. If a conclusion moved, that sentence belongs in your paper.
  • Look up the artifact or reproducibility expectations at YOUR next target venue - JOSS criteria, ACM badging, the NeurIPS checklist, or your journal's data and code availability policy - and verify the current version rather than trusting this page's snapshot.

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · What does JOSS actually require on the verification front?

The JOSS review criteria are explicit: there must be an objective way to check the software works. An automated suite with continuous integration is the "Good" answer; documented manual steps scrape by; nothing fails review. It is the clearest signal that tests moved from virtue to requirement - verify the current criteria when you submit.

2 · In the AI-assisted workflow, why does the test get written BEFORE the model drafts the implementation?

The order is the safety case. Written first, the test is an answer key the model never saw, and the arbiter is independent of the thing it judges. Written after - or worse, BY the model against its own code - it merely certifies that the code does what the code does. Your knowledge goes in the test; the model's speed goes in the middle; per the PLOS guidance, you stay reader-reviewer of the result.

3 · SciCoQA found the best LLMs caught 46.7% of 635 real paper-code discrepancies. What follows for your pre-submission audit?

46.7% means more than half the real discrepancies get past the best current tools - so AI assists the audit and cannot own it. And tests cannot close this gap either: they check code against your intent, not against your prose. The methods pass, the known-answer reproduction and the seed-change check remain human rituals with your name on the result.
